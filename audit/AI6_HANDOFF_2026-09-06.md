## Verified architecture
`src/entry.js` routes AI chat first, VIP Telegram second, then the new Telegram router, then the older Telegram ingest handler. The canonical auto webhook is `/api/telegram/webhook`; the router is therefore the effective primary implementation for that path. The scheduled handler performs Telegram webhook status checking/self-heal and notification reconciliation.

The new auto flow is designed as:
1. synchronous Telegram receipt;
2. `ctx.waitUntil(processTelegramUpdate(...))` background processing;
3. bundle photo/text intake;
4. Telegram file download;
5. R2 original-media storage;
6. vehicle AI analysis;
7. D1 `vehicle_ai_drafts` update;
8. auto-publish gate;
9. PT Xtra branded publish image;
10. D1/car image promotion;
11. final Telegram confirmation.

## Important audit finding — duplicate legacy handler
`src/entry.js` still imports `handleTelegramIngest` after `handleTelegramRouter`. The old handler also contains webhook logic. Because the router is evaluated first, `/api/telegram/webhook` is effectively owned by the router in the current entrypoint.

**Decision:** do NOT delete the legacy handler during this audit. Treat this as architecture debt and verify tests/configuration before any cleanup. Any cleanup must be a separate PR with regression coverage.

## VIP verification
`src/vip-telegram.js` accepts the VIP webhook, validates optional secret token, persists sources, downloads vehicle images to R2 when MEDIA exists, invokes vehicle AI, builds a cross-source report, and sends the report back to Telegram. It does not auto-publish.

`src/vip-vehicle-intelligence.js` explicitly separates original vehicle identity from current visual form and supports `original`, `facelift`, `up_form`, `modified`, and `uncertain`. Conflicts and uncertain form require review.

Migration `0011_vip_vehicle_intelligence.sql` creates `vip_vehicle_sessions` and `vip_vehicle_sources` with indexes and foreign-key linkage.
